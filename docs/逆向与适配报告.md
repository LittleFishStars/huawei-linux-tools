# GDIX51C0 逆向与适配报告

对象：HUAWEI MateBook X Pro（MRGF-XX）内置指纹传感器  
主机：`MRGF-XX`，Arch Linux，内核 7.2.10-arch1-1（x86_64）  
日期：2026-10-18

---

## 1. 设备定位

`lsusb` 里没有指纹设备——它不在 USB 上。设备通过 ACPI 枚举，挂在 SPI 控制器
后面：

```
/sys/bus/spi/devices/spi-GDIX51C0:00
  modalias  acpi:GDIX51C0:GDIX51C0:
  driver -> （不存在，未绑定）
```

完整路径：

```
/sys/devices/pci0000:00/0000:00:1e.2/pxa2xx-spi.6/spi_master/spi1/spi-GDIX51C0:00
```

- 控制器 PCI ID `8086:51aa`，驱动 `pxa2xx_spi_pci`，实例名 `pxa2xx-spi.6`
- ACPI 路径 `\_SB_.PC00.SPI0.SPBA`，`_ADR` = 0，`_UID` = 1，`_CID` = `GDIX51C0`
- 同控制器下 `spi0.0`（PCI `0000:00:1f.5`）绑的是 `spi-nor`，那是 BIOS flash，
  与本设备无关，不要动

内核里没有 `GDIX51C0` 的任何匹配项：

```
$ ls /sys/bus/spi/drivers/
da9052  spi-nor  wm831x
```

`spidev` 是模块（`CONFIG_SPI_SPIDEV=m`）且未加载，所以默认连 `/dev/spidev*`
都没有。

### GPIO

本机只有 `gpiochip0`，来自 `INTC1055:00`（Intel PCH 的 GPIO 控制器，
modalias `acpi:INTC1055`）。没有 `/sys/class/gpio`（libgpiod v2 只走 chardev），
也没有 `gpiochip1`。

所以复位脚与中断脚只能是 ACPI `_CRS` 里声明的 GpioIo / GpioInt 资源——这也
解释了为什么上游驱动里硬编码的 321 / 140 在本机不适用（那是另一台 MateBook
的编号，`gdix51c0.h` 的注释自己也承认应该从 `_CRS` 解析）。

## 2. 为什么不用 spidev

三条硬约束：

1. **必须拿到 GPIO。** 复位脚要拉，中断脚要等边沿。spidev 只给 SPI 字符设备，
   GPIO 得另外用 libgpiod 打开 `/dev/gpiochip0`，但 line 编号在本机未知
   （上游硬编码值不适用），要么从 ACPI 解析要么靠猜。
2. **CS 时序。** 官方驱动的写序列是 `write(hdr,4)` + `write(payload,len)`，
   两个独立的 CS 周期。spidev 上一次 `SPI_IOC_MESSAGE` 是一个连续 CS 周期，
   要复现就得拆成两次 ioctl，中间的间隔由调度器决定，不像内核里可控。
3. **10 MHz 下的分块。** 单次最多 2048 字节（`SPI_IOC_MESSAGE` 一页上限），
   内核模块里 `spi_sync` 分块没有这个限制，也不会因为 syscall 边界产生间隙。

结论：写一个真正的 `spi_driver`，ACPI 匹配，把传输与中断暴露成字符设备。

## 3. 内核模块设计

`driver/gdix51c0_fp.c`，约 640 行，`module_spi_driver` 注册。

### 匹配

```c
static const struct acpi_device_id gdix51c0_acpi_ids[] = {
    { "GDIX51C0", 0 },
    { }
};
MODULE_DEVICE_TABLE(acpi, gdix51c0_acpi_ids);
MODULE_ALIAS("acpi:" GDIX51C0_ACPI_HID);
```

### GPIO 解析

不硬编码编号，从 `_CRS` 取：

- 复位：`devm_gpiod_get_index(dev, NULL, reset_gpio_index, GPIOD_OUT_HIGH)`
- 中断：`acpi_dev_gpio_irq_get(adev, irq_resource_index)` → irq 号
- 可选电平脚：`irq_gpio_index >= 0` 时额外 `devm_gpiod_get_index`

三个都是模块参数，默认 `reset_gpio_index=0`、`irq_resource_index=0`、
`irq_gpio_index=-1`。参数错时模块仍能加载（复位与中断降级为"不可用"），
`gdix51c0 info` 会把 `reset_valid` / `irq_gpio_valid` 报出来。

### 设备接口

`/dev/gdix51c0`，`MISC_DYNAMIC_MINOR`，mode 0600。

ioctl（`MAGIC 0xD1`）：

| 编号 | 名字 | 作用 |
| --- | --- | --- |
| `0xC0D10101` | `IOC_XFER` | 全双工搬运，`struct gdix51c0_xfer_req` |
| `0xC004D102` | `IOC_RESET` | 拉复位，参数为保持微秒数 |
| `0x8000D103` | `IOC_INFO` | 读 `struct gdix51c0_info` |
| `0x8000D104` | `IOC_IRQ_COUNT` | 读累计中断计数（u64） |
| `0x8000D105` | `IOC_IRQ_LEVEL` | 读当前电平 |
| `0xC004D106` | `IOC_IRQ_WAIT` | 等下一个边沿，参数为超时毫秒 |

```c
struct gdix51c0_xfer_req {
    __u32 tx_len, rx_len, speed_hz, flags;
    __u64 tx_buf, rx_buf;
};

struct gdix51c0_info {
    char hid[16];
    __u32 irq, reset_valid, reset_active_low, speed_hz, chunk, irq_gpio_valid;
};
```

`IOC_XFER` 的语义：时钟数是 `max(tx_len, rx_len)`；`tx_len < rx_len` 时多出来的
周期 MOSI 填 `0xff`（这是全双工读的标准做法，上游明确说不能用半双工
`read()`，否则图像会错位）。内部分块，每块不超过 `chunk_bytes`（默认 2048）。

### sysfs

`info`（只读摘要）与 `irq_count`，方便不写代码时看状态。

### 编译坑

内核 7.2 移除了 `no_llseek`，`file_operations` 里不能写 `.llseek = no_llseek`。
最初照 5.x 的写法编译失败，删掉该行即可（`unlocked_ioctl` 现代表非 seekable）。

## 4. 线协议

### 4.1 帧结构

```
外框 4B:   type(1) | len_lo(1) | len_hi(1) | csum(1)
载荷 lenB: cmd(1)  | inner_len(2, LE) | data... | csum(1)
```

两个校验和都是

$$csum = (0xaa - \sum \text{前面所有字节}) \bmod 256$$

外框 `type` 表示搬运类别：`0xa0` = 主机写，`0xb0` = 主机读 / ack。载荷首字节
才是命令号。`inner_len` 含末尾校验和，因此 `inner_len = len(data) + 1`。

特殊值 `0x88` 是"空校验和"，出现在硬编码握手帧和某些 ack 里，解析时要放行。

### 4.2 命令号

| 值 | 名称 | 值 | 名称 |
| --- | --- | --- | --- |
| `0x00` | NOP | `0x96` | ENABLE_CHIP |
| `0x20` | GET_IMAGE（背景） | `0x98` | SET_DAC |
| `0x22` | GET_IMAGE（带手指） | `0xa2` | RESET |
| `0x32` | FDT_DOWN | `0xa6` | READ_OTP |
| `0x34` | FDT_UP | `0xa8` | FIRMWARE_VERSION |
| `0x36` | FDT_MODE | `0xae` | QUERY_MCU_STATE |
| `0x50` | NAV | `0xaf` | GET_MCU_STATE |
| `0x70` | IDLE | `0xb0` | ACK |
| `0x80` | WRITE_SENSOR_REG | `0xd0` | REQUEST_TLS |
| `0x82` | READ_SENSOR_REG | `0xd4` | TLS_ESTABLISHED |
| `0x90` | UPLOAD_CONFIG | `0xe0` | PRESET_PSK_WRITE |
| `0x94` | POWERDOWN_FREQ | `0xe4` | READ |

`0x17` 不是命令号，是 TLS 应用数据记录的 content type——图像就装在里面。

### 4.3 初始化序列

1. `PREFIX01` = `01 05 00 00 00 00 00 88`，不等 ack，等 10 ms
2. 读 EVK 版本：`a8 03 00 00 00 ff`。失败则硬复位 + 500 ms，共 3 轮
3. 再发一次 `PREFIX01` → 10 ms → 查 MCU 状态：
   `af 06 00 55 ms_lo ms_hi 00` + `00` + `csum+1`（9 字节，校验和是 +1 变体）
4. `RESET` 命令 `0xa2`，data = `[1, 0x14]`（复位传感器，非软复位，睡 0x14）
5. 读芯片 ID：`0x82` + `register_read(0, 4)`，响应 4 字节
   `[status, lo, hi, rsv]`，取 `lo | hi<<8` = `0x2504`
6. 读 OTP：`0xa6 03 00 00 00 01` → 64 字节
7. 从 OTP 取自校准 DAC：优先 `OTP[0x32..0x35]`（ft dac），空则
   `OTP[0x2E..0x31]`（mt dac），都空则退回 `0x0b38/0xb5/0xb3/0xb3`。
   主值换算 `main = (dac[0] << 4) | 8`
8. 再 `RESET`
9. `IDLE` `0x70`，data = `[0x14, 0]`
10. `SET_DAC` `0x98`，12 字节：`98 09 00 main_lo main_hi d1 00 d2 00 d3 00 csum`
11. `UPLOAD_CONFIG` `0x90`，232 字节配置块（见 4.4）
12. 等 200 ms，drain

### 4.4 配置块

232 字节，静态模板，其中几个字段要按 DAC 与时序改写：

| 偏移 | 内容 |
| --- | --- |
| 118 | 寄存器 `0x005c`（默认 `0x0110`） |
| 122 | DAC main（LE16） |
| 126 | DAC 1 |
| 130 | DAC 2 |
| 134 | DAC 3 |
| 178 | 寄存器 `0x0082`（默认 `0x1d80`） |

校验和有两层：

```
内层（cfg[3:231]）: total = 0xA5A5; for i in range(0, len-2, 2): total += LE16()
                    csum = (-total) & 0xffff   → 写回 cfg[229..230]
外层（整块）      : cfg[231] = (0xaa - sum(cfg[:231])) & 0xff
```

**时序必须跟着 DAC 一起改。** 旧时序配新偏置会让模拟读出无法完成，表现为图像
在固定行截断。只有 `dac_main != 0x0b38` 时才应用新时序。

### 4.5 采图

```
清掉陈旧的 0x17 包
→ （首次）等 10 ms
→ GET_IMAGE（0x20 或 0x22），等 ACK
→ ★ 等 80 ms，期间 SPI 上不能有任何时钟
→ 读一条 TLS 记录，超时 1 s
→ 校验 record[0] == 0x17
→ TLS 解密 → RAW12 解码 → 64×80 像素
```

那 80 ms 是硬约束。上游注释写得很清楚：读阵列约 73 ms，Windows 驱动在这期间
SPI 上完全静默；如果主机的异步 listener 在这时轮询并读走数据，模拟读出会在
固定行被截断（社区叫 "row-31 cliff"，错误码 `0x0b78`）。

上游的解法是 `listener_set_suppress(TRUE)` + sleep + `FALSE`，并且在 poll 唤醒
分支里删掉 `continue`，让流程走到"先查 suppress、再读 IRQ 电平、仍为高才读
SPI"的逻辑。本项目没有后台线程，静默窗口天然成立——这是同步实现的一个
意外好处。

### 4.6 RAW12 解码

7680 字节 → 5120 个 12 bit 像素。每 6 字节一组产出 4 个像素：

```
p[0] = ((s0 & 0x0f) << 8) | s1
p[1] = (s3 << 4) | (s0 >> 4)
p[2] = ((s5 & 0x0f) << 8) | s2
p[3] = (s4 << 4) | (s5 >> 4)
```

解码后按 80 列 × 64 行排布（80 是慢轴、64 是快轴）。上游的
`GDIX51C0_SENSOR_WIDTH 64` / `HEIGHT 80` 指的是快/慢轴，落图时要转置。

## 5. TLS 与 PSK

### 5.1 通道

- `TLS_server_method()`——**传感器是 TLS 服务端，主机是客户端**
- min = max = TLS 1.2
- cipher 固定 `PSK-AES128-GCM-SHA256`
- `SSL_VERIFY_NONE`
- PSK identity 字符串 `"Client_identity"`（15 字节）
- 握手完成后等 100 ms，发 `0xd4`（TLS_ESTABLISHED），不可省——这是 MCU 的
  状态迁移

上游用自定义 BIO 把 TLS 记录直接压在 SPI 上，写时用 `0xb0` 外框。本项目用
Python 的 `MemoryBIO` + `SSLObject`，同样的语义，但没有 OpenSSL 的 BIO 回调
复杂度。

两条入站修补（上游 `gdix51c0_patch_inbound`）：

1. 空的 ChangeCipherSpec `14 03 03 00 00 00` 要补成 `14 03 03 00 01 01`
2. ClientKeyExchange 里的 identity 被截断时，按前缀
   `16 03 03 00 15 10 00 00 11 00 0f`（11 字节）还原 15 字节 `Client_identity`

### 5.2 White-box 容器

传感器不收裸 PSK，只收 102 字节容器，写进寄存器 `0xbb010003`：

```
front(32) | hdr(2) | len(4) | h16(16) | ct(32) | tag(16)
```

- `hdr` = `02 ff`，`len` = `uint32_le(32)`
- `h16` = `SHA256(hdr | len | psk[0:8] | (03 00 00 00)×16)[0:16]`
- `ct, tag` = `AES-256-GCM(KEY, iv=h16, aad=AAD, pt=psk)`
- `front` = `HMAC-SHA256(HMAC_KEY, hdr | len | ct | tag)`

`KEY` 与 `HMAC_KEY` 从同一段 48 字节常量里切，**重叠 16 字节**
（`KEY = kbuf[0:32]`，`HMAC_KEY = kbuf[16:48]`）。这个重叠是逆向
`gfspi.dll` 的 `whitebox_wrap` 得到的，不是笔误。

用上游 `gdix51c0-wb.c` 的 selftest oracle 验证过：PSK = `00..1f` 时容器必须
逐字节等于

```
45a3732acf2990f4ceb30e8996e4add12e887160d6dcaa99c8bcd8338c7743f2
02ff20000000e7bc09962aedfb470fac3887de32465c5a71c88fe01dd776cfa5
19e70c63f82401f8247324fde9c6562321d4d82b0dd552c0bf1f74716085b852
658bfe772964
```

本项目的 `psk.wrap()` 与之一致，`selftest` 里有这条断言。

### 5.3 部署

`0xe0` 命令，data 布局：

```
addr(LE32 = 0xbb010003) | len(LE32 = 102) | WB(102) | 4 字节对齐填充
```

总长 4+4+102 = 110，补 2 字节到 112。

**这是破坏性操作**：传感器里旧密钥被覆盖，之后 Windows 侧与任何其它主机都要
重新部署同一把密钥才能通信。CLI 里因此要求 `--yes`。

## 6. 与上游实现的差异

参考 [libfprint-goodix-spi](https://github.com/berkekbgz/libfprint-goodix-spi)
（LGPL-2.1-or-later，pre-release，只在 MateBook 16s 验证过）。

| 方面 | 上游 | 本项目 |
| --- | --- | --- |
| SPI 通路 | spidev（用户态） | 真内核模块 |
| GPIO | 硬编码 321/140，环境变量可覆盖 | 从 ACPI `_CRS` 解析，模块参数选序号 |
| 中断处理 | 后台 listener 线程 + poll + eventfd | 同步 IOCTL，无后台线程 |
| 静默窗口 | `set_suppress(TRUE/FALSE)` 抑制 listener | 天然无竞争 |
| 集成方式 | 给 libfprint 打补丁做影子库 + 改 fprintd | 独立 CLI 工具 |
| 语言 | C（GLib） | 内核 C + 用户态 Python |

上游的异步模型带来一个真实 bug：采图静默期内 IRQ 升高被 poll 消耗，静默结束
后代码只等新边沿，于是超时并报
`timed out awaiting cmd 0x17 after 1000000 us`。社区（xingwangzhe.fun，
2026-10-11，MateBook D15 BoF-XX）的修复是让 suppress 解除时向 eventfd 写计数
唤醒，并删掉 poll 内部唤醒分支里的 `continue`。本项目从设计上避开了这个问题。

## 7. 未完成与后续

- **真机验证。** 开发环境无 root（`sudo -n` 失败），无法 `insmod`，也无法
  `acpidump` 读 `_CRS`。因此 `reset_gpio_index` / `irq_resource_index` 的
  实际取值是推断的（默认 0/0），需要在真机上用 `gdix51c0 info` 确认
  `reset_valid` 与 `irq_gpio_valid` 都为真
- **fprintd 集成。** 目前是独立 CLI。要接成系统认证需要写 libfprint 后端
  （`FpImageDevice` 子类）或用 NBIS 的 `bozorth3` 做匹配。本机没有
  mindtct/bozorth3 包
- **FDT 阈值标定。** `arm_finger_detect` 走的是手动 FDT 模式（cmd `0x36`，
  mode `0x09`），detect-up 的阈值数组还没按本机传感器标定
- **Linux 7.2+ 的 eSPI 路线。** 社区有 `drivers/misc/gxfp5130` 的 LKML 补丁
  （2026-07-18，Metehan Günen），针对 MateBook D16 2024 / X Pro 2024，走 eSPI
  信箱 + 3 GPIO。与本机的 SPI 通路不同，但结构上可参考；如果后续 Huawei 改用
  eSPI，那条路线才是正解
