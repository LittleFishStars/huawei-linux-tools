# 华为 MateBook X Pro 2023 内置 NFC（ACPI\NTAG0001）Windows 驱动逆向与 Linux 适配报告

> 目标：把随机附带的 Windows 版 NFC 驱动逆向清楚，并在当前 Arch Linux 上落地可用的方案。
> 样本：`HUAWEI_MateBook_X_Pro_2023_13代酷睿版_NFC_23.2.3.0.zip`
> 分析机：MRGF-XX（MateBook X Pro 2023，13 代酷睿），内核 `7.2.10-arch1-1`

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 硬件是什么 | ACPI 设备 `NTAG0001`（`\_SB_.PC00.NFC_`），挂在 **Intel LPSS I2C 控制器 `0000:00:15.0`（i2c-0）** 上，另有一根 **GpioInt** 中断线 |
| Linux 内核认不认 | **认识设备，不认识驱动**：内核已按 ACPI `_CRS` 建好 i2c client `i2c-NTAG0001:00`，但 `nxp-nci_i2c` / `pn544_i2c` 的 ACPI 匹配表里都没有 `NTAG0001`，所以没有任何驱动绑定 |
| Windows 驱动是什么 | `SpbNfcDriver.sys`，**KMDF 框架 + CNG(HMAC-SHA256)** 的私有驱动；**不导入 `nfccx.sys`**（没有走 Windows NFC 类扩展），也没有一行标准 NCI 编解码 |
| 它到底干什么 | 它是一个**搬运工 + 私有控制协议**：按 ACPI 资源打开 I2C 目标（`\Device\RESOURCE_HUB\<64bit id>`），把用户态的私有 16 字节块发给芯片、收回来、用 HMAC-SHA256 校验，再回给用户态。**NFC 协议栈本身不在这个包里**（包里只有驱动，没有 NFC 应用） |
| Linux 上最快的路 | 三种姿势，按推荐顺序见 §6：① 给 mainline `nxp-nci` 加 ACPI ID（若芯片真是 NXP NCI）；② 用本报告的通用探针模块 `ntag_nfc.ko` 直接问芯片；③ 复刻华为私有协议（代价最高，且缺用户态对端） |

**一句话**：Windows 驱动里没有 NFC 协议栈，只有一层私有搬运协议；Linux 适配不应该移植这个驱动，而应该**直接跟芯片说 NCI**。为此本报告交付了一个探针内核模块与用户态工具，用来在几分钟内判定芯片是否说 NCI。

## 2. 硬件与固件侧事实（无需 root 即可复现）

```
$ ls /sys/bus/i2c/devices/ | grep NTAG
i2c-NTAG0001:00

$ cat /sys/bus/i2c/devices/i2c-NTAG0001:00/{name,modalias,uevent}
NTAG0001:00
acpi:NTAG0001:
MODALIAS=acpi:NTAG0001:

$ readlink -f /sys/bus/i2c/devices/i2c-NTAG0001:00
/sys/devices/pci0000:00/0000:00:15.0/i2c_designware.0/i2c-0/i2c-NTAG0001:00

$ readlink -f /sys/bus/i2c/devices/i2c-NTAG0001:00/firmware_node
/sys/devices/LNXSYSTM:00/LNXSYBUS:00/PNP0A08:00/NTAG0001:00     # ACPI 路径 = \_SB_.PC00.NFC_
```

要点：

1. **设备已被内核枚举**：`0000:00:15.0` 是 Intel Alder Lake-P PCH Serial IO I2C Controller #0（PCI ID `8086:51e8`），`i2c_designware` 驱动接管后建出 `i2c-0`，ACPI 又在其上建出 `NTAG0001:00` 这个 client。
2. `i2c-NTAG0001:00/` 下**只有 `name/modalias/uevent/power/` 和一个 `waiting_for_supplier`**——没有 `driver` 符号链接，说明它处于「等驱动」状态。
3. **从地址（slave address）与 GPIO 中断号不暴露在 sysfs**（`i2c_device` 的 `addr` 属性在 6.x 才加入 `i2c-dev` 侧，且这里没有）。它们写在 ACPI `_CRS` 里：
   ```
   I2cSerialBus(0x????, ControllerInitiated, 0x00061A80, AddressingMode7Bit, "\\_SB.PCI0.I2C0", ...)
   GpioInt(Level|Edge, ActiveLow/High, ..., "\\_SB.GPI0", ...)
   ```
   读法（需要 root）：
   ```bash
   sudo cat /sys/firmware/acpi/tables/DSDT > /tmp/dsdt.aml
   # Arch 下装 acpica 工具后：iasl -d /tmp/dsdt.aml; grep -A40 -i NTAG0001 /tmp/dsdt.dsl
   # 或者直接 sudo i2cdetect -y -r 0 扫一遍
   ```
   > 本报告的探针模块会在 probe 时**直接把从地址与中断号打印到 dmesg**，这是最省事的获取方式。
4. 同一条 i2c-0 上还挂着 `GXTP7863:00`（Goodix 触屏，GpioInt），说明这条总线上确实跑着「非 HID-over-I2C 的普通 ACPI client」，`NTAG0001` 属于同类。
5. 内核**已经带了 NFC 子系统**：`CONFIG_NFC=m`、`CONFIG_NFC_NCI=m`、`CONFIG_NFC_NXP_NCI=m`、`CONFIG_NFC_NXP_NCI_I2C=m`（模块在 `/lib/modules/7.2.10-arch1-1/kernel/drivers/nfc/`）。
   `nxp-nci_i2c` 的 ACPI 别名只有 `NXP7471` / `NXP1002` / `NXP1001`，`pn544_i2c` 只有 `NXP5440` —— **没有一个能匹配 `NTAG0001`**，这正是本机 NFC 用不了的直接原因。

`install.cmd` 的核心：`devcon.exe update SpbNfcDriver.inf "ACPI\NTAG0001"` —— 也就是说**华为是拿微软的 SPB 外设示例驱动改名、改成自己的私有协议**（INF 里 `DiskId1 = "SPB Test Tool Peripheral Installation Disk #1"` 明确暴露了血统）。

### INF 关键内容

```ini
Class      = HIDClass                     ; ← 挂在 HID 类下（不是 NFC 类！）
ClassGuid  = {745a17a0-74d3-11d0-b6fe-00a0c90f57da}
Provider   = "Huawei Device Co., Ltd."
DriverVer  = 02/10/2023,23.2.3.0
[Standard.NTamd64]

[SpbNfcDriver_AddReg]

[SpbNfcDriver_Install.NT.Services]

```

配合驱动里的 `WdfDeviceCreateDeviceInterface(&GUID_DEVCLASS_PORTS, …)`，用户在 Windows 上看到的是 `\Device\NFCDevice` 与 `\DosDevices\SPBNFCDRIVER` 两个名字，而**对外暴露的设备接口是 PORTS 类 GUID**——典型「不按规范办事的私有外设」。

`NFC.exe`（第一层解出来的那个）经检查是**纯 NSIS 安装器**（导入表只有 kernel32/user32/shell32/advapi32/ole32，节名 `.ndata`），**这个包里没有任何 NFC 用户态程序**。所以「NFC 应用逻辑」（碰一碰、配对、读写卡）不在我们手里。

## 4. `SpbNfcDriver.sys` 静态分析

工具：Ghidra 12.1 + objdump 交叉核对；产物 `/home/ylxc/nfc-re/sys.dis`（5591 行全反汇编）、Ghidra 工程。

### 4.1 总体形态

| 项 | 值 |
|---|---|
| 框架 | **KMDF**（`.kmdfclassbind$*` 段、`WdfVersionBind/WdfVersionBindClass` 来自 `WDFLDR.SYS`），DriverPoolTag `'SPBT'` |
| 导入（ntoskrnl） | `KeSetEvent/KeClearEvent/KeInitializeEvent`、`IoSetDeviceInterfaceState`、`IoRegisterDeviceInterface`、`IoWMIRegistrationControl`、`memcpy_s`、`RtlCopyUnicodeString/InitUnicodeString`、`MmGetSystemRoutineAddress`、`_vsnwprintf` |
| 导入（cng.sys） | `BCryptOpenAlgorithmProvider/GetProperty/CloseAlgorithmProvider/CreateHash/DestroyHash/HashData/FinishHash` |
| **没有导入** | `nfccx.sys`（NFC 类扩展）、`ntnfc.sys`、任何 NCI 相关符号 |
| 调用约定 | 函数表指针 `[0x140007378]`、驱动全局 `[0x140007380]`；每次 WDF 调用 = `rax = WdfFunctions[偏移]; rcx = WdfDriverGlobals; call __guard_dispatch_icall`，故反编译里看到的「第一个参数」其实是隐式的 WDF 全局 |

驱动一共 75 个函数、约 18.5 KB 代码，其中 4 个是 WPP/ETW 跟踪桩（`FUN_140009000` 一族），与业务无关。

### 4.2 设备上下文布局（从多个例程交叉验证得出）

| 偏移 | 类型 | 含义 |
|---|---|---|
| `+0x00` | WDFDEVICE | 设备对象 |
| `+0x08` | WDFQUEUE | 内部队列句柄 |
| `+0x10` | u32 | **I2C 连接的 64 位 ConnectionId 低半**（来自 ACPI `_CRS`） |
| `+0x14` | u32 | ConnectionId 高半 |
| `+0x18` | WDFINTERRUPT | 中断对象（`WdfInterruptCreate` 产生） |
| `+0x20` | KEVENT | 同步事件 |
| `+0x38` | u8 | `Settings\isInterrupt`（要不要用中断） |
| `+0x40` | WDFIOTARGET | 打开后的 I2C 目标句柄 |
| `+0x48` | WDF 对象 | 内部 I/O 请求/内存对象 |
| `+0x50` | 句柄 | 辅助对象 |
| `+0x58` | WDFREQUEST | 正在处理的客户端请求 |
| `+0x60` | WDFREQUEST | **可取消的挂起请求**（中断到来时完成它） |
| `+0x68/+0x69` | u8×2 | 两个状态/标志字节 |
| `+0x6c` | u32 | HMAC 模式（1 / 2，见 §4.5） |
| `+0x70` | BCRYPT_HASH_HANDLE | CNG 哈希句柄 |
| `+0x78` | BCRYPT_ALG_HANDLE | CNG 算法句柄 |
| `+0x90` | u32 | `HashDigestLength`（=32） |
| `+0x9a` … | 4×32B | **摘要表 A**（bank A） |
| `+0x11a` … | 4×32B | **摘要表 B**（bank B） |

设备上下文的 8×SHA256 摘要初值来自 `.rdata 0x140006190` 起的 0x100 字节常量，在 `EvtDeviceAdd` 里被 `memcpy_s` 拷进去——也就是说**驱动内置了两组（各 4 个）32 字节的期望值**，运行时用 HMAC-SHA256 算出来跟它们比。载体就是标准 SHA-256 的初始向量/轮常量，所以 `ghidra_detect_crypto_constants` 一撞一个准。

### 4.3 关键例程（函数级）

| 函数 | 角色 | 要点 |
|---|---|---|
| `FUN_140001b04` | `DriverEntry` | `WdfDriverCreate`，`EvtDriverDeviceAdd=FUN_140001000`，pool tag `'SPBT'`；随后 `WdfDriverCreateDeviceInterface`, `IoWMIRegistrationControl` |
| `FUN_140001000` | `EvtDeviceAdd` | 读注册表 `Settings\isInterrupt` → `+0x38`；建 2 个队列：队列0（`EvtIoRead=FUN_1400021c0`），队列1（`EvtIoWrite=FUN_140002b40`、`EvtIoDeviceControl=FUN_140002d20`、`EvtIoInternalDeviceControl=FUN_1400025c0`）；`WdfDeviceCreateSymbolicLink("\DosDevices\SPBNFCDRIVER")`；`WdfDeviceCreateDeviceInterface(GUID_DEVCLASS_PORTS)` |
| `FUN_140002770` | `EvtDevicePrepareHardware` | **资源解析**（见下） |
| `FUN_140002460` | 中断回调 | 取设备上下文，调 `FUN_1400039e4`；若有挂起请求则 `KeClearEvent(+0x20)` |
| `FUN_1400039e4` | 中断下半部 | 若 `+0x60` 有请求：`WdfRequestUnmarkCancelable` → 成功则 `WdfRequestComplete(req, 0)`，`STATUS_CANCELLED` 则静默返回 |
| `FUN_140003e50` | 取消例程 | 清 `+0x60`，`WdfRequestComplete(req, 0xC0000120=STATUS_CANCELLED)` |
| `FUN_140003fb0` | **打开 I2C 目标** | `id64 = *(u64*)(devctx+0x10)`；用 `"%0*I64x"` 格式化 → 与 `"\Device\RESOURCE_HUB\"` 用 `"%s%s"` 拼成设备名 → 填 0x88 字节的 `WDF_IO_TARGET_OPEN_PARAMS`（访问 `0xC0000000`、`ShareAccess=1`）→ `WdfIoTargetOpen`，句柄存 `+0x40` |
| `FUN_1400041e0` | 提交路径 | 请求存 `+0x58`，格式化后 `FUN_1400043a4` 真正发 I2C，失败走 `FUN_140003838` |
| `FUN_1400043a4` | Send | 建请求上下文，`WdfRequestSetCompletionRoutine(FUN_140003c90)`，然后 `WdfIoTargetSendIoctlSynchronously`/`WdfRequestSend` 一族，最后完成客户端请求 |
| `FUN_140003c90` | I/O 完成例程 | 从 `WDF_REQUEST_COMPLETION_PARAMS` 取 `IoStatus.Status/Information`，回填并调 `FUN_140003838` |
| `FUN_140003838` | 回客户端 | 若 `+0x58` 有请求则 `WdfRequestCompleteWithInformation` |
| `FUN_140001d80` | 加密初始化 | `BCryptOpenAlgorithmProvider("SHA256", 0x20)`（`0x20 = BCRYPT_ALG_HANDLE_HMAC_FLAG` → **HMAC-SHA256**）+ `BCryptGetProperty("HashDigestLength")` → `+0x90` |
| `FUN_140003570` | **私有协议状态机** | 见 §4.4 |
| `FUN_140004784` | 第二 I/O 处理 | 取请求内存块 → `FUN_140003570` 解析 → 写 `devctx+0x40` 目标 → 建内部请求 → `FUN_1400043a4` |

### 4.4 资源解析（`EvtDevicePrepareHardware`，已逐条对照汇编确认）

循环遍历 **Translated** 资源列表，用 `WdfCmResourceListGetDescriptor` 取描述符，看第一个字节（`CM_PARTIAL_RESOURCE_DESCRIPTOR.Type`）：

```
Type == 0x02 (CmResourceTypeInterrupt)
    → 记录中断描述符索引（重复出现则打 WPP 0xe）
Type == 0x84 且 [desc+4] == 2 (Class = SERIAL) 且 [desc+5] == 1 (Type = I2C)
    → 记录连接：
        *(u32*)(devctx + 0x10) = *(u32*)(desc + 8)
        *(u32*)(devctx + 0x14) = *(u32*)(desc + 0xc)     // 64 位 ConnectionId
      重复出现则打 WPP 0xc
```

- 找不到「连接」资源 → 直接失败返回 `0xC0000225`（`STATUS_NOT_FOUND`）；
- `+0x38`（注册表 `isInterrupt`）为 1 且找到中断 → 现场构造 0x68 字节的 `WDF_INTERRUPT_CONFIG`（`Size=0x68`、回调 `FUN_140002460`、`InterruptRaw/Translated` 来自两次描述符查询、`+0x58=1`、`+0x5c=2`）→ `WdfInterruptCreate` → 成功后 `KeInitializeEvent(+0x20, 1, 0)`；
- 最后调 `FUN_140001d80` 初始化 HMAC-SHA256。

> 结论：**驱动完全不含 I2C 地址**，它只持有 ACPI 给的「连接 ID」，再由 Resource Hub 把名字翻译成 I2C 传输参数。地址属于固件（ACPI `_CRS`）。

### 4.5 华为私有 16 字节协议（`FUN_140003570`）

用户态（Windows 上的 NFC 服务）通过 IOCTL / 写请求送进来的数据，被按如下规则解析：

```
len < 2                     → 失败
pkt[0] = 块类型, pkt[1] = 命令类
  0x10  (2..9 字节)  → FUN_1400032b4：读 pkt[6]
                           0x33 → 用 bank A 的两个 9 字节摘要做校验：命中 state=1，否则 state=2
                           0x02 → state=3                （进入"已认证"状态）
  0x20  (state!=3)   → FUN_140004914(pkt+2, bankB[0], bankB[1], 9,  ctx)
  0x30  (state!=3)   → FUN_140004914(pkt+2, bankB[2], bankB[3], 0x19, ctx)
  0x40  (state==3?)  → FUN_140004a74(pkt+0xb, 7, ctx)  或  FUN_140004914(pkt+2, bankB[4..], 0x29, ctx)
  0x50               → 仅 state==3 继续
  0x60               → state==3 时 FUN_140004a74(pkt+2, 9, ctx)
  0x70               → FUN_14000343c(pkt, 0x12, ctx)
  0x80               → FUN_140004a74(pkt+2, 0x10, ctx)
  0x90               → FUN_140004a74(pkt+2, 0xa,  ctx)
```

配套机制：

- **分块 HMAC 调度** `FUN_140004914`：按 `+0x6c` 的模式（1 用 bank A、2 用 bank B）把数据按 16 字节块（上限 0x32 字节）喂给 `FUN_140003190`/`FUN_14000306c`；模式非法或超长直接打 WPP 0x3e/0x3f 返回失败。
- **两套摘要表**（各 4×32 字节）—— 典型的**挑战/应答配对白名单**：驱动预置「哪台设备能配对」的期望值，用户态送来的 16 字节块与之比对，对了就把状态推到 `state=1/3`，之后才允许 0x50/0x60 这类数据通道命令。
- **IOCTL 面**：整份二进制里只出现三个自研 IOCTL 码 `0x4001C00` / `0x4001C04` / `0x4001C20`（`FUN_1400045c8`、`FUN_140003fb0`、`FUN_140003768`），**没有任何 `IOCTL_SPB_*`** —— 它不走 SPB 的 `IOCTL_SPB_EXECUTE_SEQUENCE`，用的是自己拼请求再 `WdfIoTargetSend…`。
- **全库没有任何 NCI 命令常量**（没有 `0x20 0x00 CORE_RESET`、`0x21 0x03 RF_DISCOVER`、`0x2F …`）—— **芯片协议不由驱动解释**，它只搬字节。

### 4.6 由 4.5 推出的架构判断（高置信）

```
Windows:  [NFC 服务/应用]  --私有 16B 块协议-->  SpbNfcDriver.sys  --原始 I2C 字节-->  芯片
Linux:                     --NCI/nfctool-->     nxp-nci(或本探针模块)  --I2C-->        芯片
```

也就是说：**华为把「NFC 协议栈 + 配对逻辑」放在了 Windows 用户态**（这解释了为什么包内只有驱动、为什么驱动里只有校验和搬运、为什么它连 nfccx 都不用）。这对我们是好消息——我们要替换的不是驱动，而是「协议栈」；而 Linux 恰好自带 NFC 协议栈（`net/nfc` + `nfctool`）。

## 5. 为什么不能把这个 Windows 驱动「移植」到 Linux

1. **框架不可移植**：整个驱动是 KMDF 回调模型（`EvtDevicePrepareHardware`/`WDFQUEUE`/`WDFINTERRUPT`/`WDFIOTARGET`），Linux 没有对应物，逐行翻译没有意义。
2. **传输通道是 Windows 专有**：`\Device\RESOURCE_HUB\<id>` 是 Windows SPB/Resource Hub 的私有设备名，Linux 的等价物是 ACPI 里已解析好的 `i2c_client`（内核已经帮我们建好了）。
3. **它不实现 NFC 协议**：把驱动搬过去也不会有任何可用功能——NFC 的 RF 发现、卡模拟、NDEF 读写全在别处。
4. **私有协议缺对端**：`0x10..0x90` 那套命令需要一个对应的用户态对端，而这个包**不含任何 NFC 应用**（`NFC.exe` 是 NSIS 安装器）。
5. 它只在 `isInterrupt` 打开时才用中断，且中断语义是「唤醒挂起的 16 字节应答」，与 NFC 标准的中断语义（数据就绪）不同。

**因此适配策略是「重新接入标准栈」，而不是「移植」。**

## 6. Linux 适配方案

### 6.0 三条路线

| 路线 | 适用前提 | 工作量 | 结果 |
|---|---|---|---|
| **A. 复用 mainline `nxp-nci`** | 芯片确实是 NXP NCI 控制器（`NTAG0001` 只是华为的 ACPI 别名） | 改 2 行 ACPI 匹配表 + 可能调 GPIO 序号 | 得到完整的、上游维护的 NFC 栈（`nfctool` 立刻可用） |
| **B. 通用探针模块**（本报告交付） | 未知芯片 | 已写好，`make && insmod` | 立刻得到：从地址、中断号、芯片对 `CORE_RESET` 的原始应答 → 判定是否 NCI |
| **C. 复刻华为私有协议** | 已经确定芯片不说 NCI，且能拿到 Windows 侧用户态程序 | 很大 | 能碰一碰，但逆不出用户态就毫无意义 |

**推荐执行顺序：B → A（若 B 证明是 NCI 或 NXP 芯片）→ C（兜底）。**

> 线索：Android 内核（realme sm6150）里有一个提交叫 *"NFC: Add driver support for NTAG"*，把 `NTAG` 加进 `nxp-nci` 的 ACPI 匹配表：
> `https://github.com/dev-harsh1998/android_kernel_realme_sm6150/commit/e9c434c26482368748ed61bd991679067f6c2229`
> 这与「华为用 `NTAG0001` 当 NXP NCI 芯片的 ACPI ID」的判断一致。（本机 hosts 劫持了 `github.com`，无法直接取正文，请自行核对。）

### 6.1 路线 B：探针模块（已交付，立刻可跑）

```bash
cd /home/ylxc/nfc-re/linux
sudo pacman -S --needed base-devel linux-headers     # 需要与当前内核匹配的 headers
make
sudo insmod ntag_nfc.ko          # 装载即自动探测（probe_on_load=1）

sudo dmesg | grep -i ntag
# 期望看到：
#   ntag_nfc ...: 绑定成功: adapter=i2c_designware.0(nr=0) i2c_addr=0x?? irq=???
#   ntag_nfc ...: 中断 ?? 已注册(下降沿, oneshot)
#   ntag_nfc ...: 已创建 /dev/ntag_nfc
#   ntag_nfc ...: probe: write NCI CORE_RESET_CMD [4] 20 00 01 01
#   ntag_nfc ...: probe: response [32] XX XX XX ...
```

模块给出的东西：

- `i2c_addr`：**ACPI 声明的从地址**（我们之前拿不到的那个数字）；
- `irq`：GpioInt 中断号，以及「中断能不能注册成功」（`IRQ_TRIGGER_FALLING`）；
- `/dev/ntag_nfc`：`write()` = 原始 I2C 写，`read()` = 原始 I2C 读（协议逆向用）；
- `.../ntag_nfc/info`、`.../ntag_nfc/last_rx`、`.../ntag_nfc/warm_reset`：sysfs 观察点。

判读规则（`reset` 探测部分的写法覆盖了 4 种常见组帧）：

| 收到的字节 | 结论 |
|---|---|
| `40 00 01 00` | **标准 NCI**，`CORE_RESET_RSP`，status=0 → 走路线 A，芯片可用 `nfctool` 驱动 |
| `60 00 …` | 收到 `CORE_RESET_NTF`，后面的字节通常含厂商 ID / 芯片型号（下面就是 `nxp-nci` 的驱动名） |
| 全 `00` / 全 `FF` / 读失败 | 可能是非 NCI 私有芯片，或需要先做「使能/复位 GPIO 时序」（Windows 侧有 `isInterrupt`，说明它有独立的使能流程），转路线 C |
| 写就 NAK（`-EREMOTEIO`） | 地址不对（用 `sudo i2cdetect -y -r 0` 复核），或芯片未上电 |

### 6.2 路线 A：给 mainline `nxp-nci` 加 `NTAG0001`

补丁见 `linux/0001-nfc-nxp-nci-add-NTAG0001.patch`。要点：

```c
 static const struct acpi_device_id nxp_nci_i2c_acpi_match[] = {
 	{ "NXP1001", 0 },
 	{ "NXP1002", 0 },
 	{ "NXP7471", 0 },
+	{ "NTAG0001", 0 },
 	{ }
 };
```

以及 GPIO 映射（`nxp-nci` 用 `_DSD` 风格的 `enable-gpios`/`firmware-gpios`，序号固定写死为 1 和 2）：

```c
 static const struct acpi_gpio_params enable_gpios   = { 1, 0, false };
 static const struct acpi_gpio_params firmware_gpios = { 2, 0, false };
```

华为的 `_CRS` 里到底有几个 GpioIo（0/1/2 个都可能），需要按 `probe` 的报错调整这两个序号；如果根本没有使能 GPIO，就要把
`devm_gpiod_get(dev, "enable", …)` 改成 `devm_gpiod_get_optional`，否则 probe 会以 `-ENOENT` 失败。

最稳的验证方式（不用改内核、不用重编译）：

```bash
sudo modprobe nxp-nci_i2c
echo NTAG0001 | sudo tee /sys/bus/i2c/devices/i2c-NTAG0001:00/driver_override  # 需内核支持
```

或者临时给模块传参/用 `new_id` 之类的机制，把 client 手工绑到已加载的 `nxp-nci_i2c` 上。

### 6.3 路线 C：复刻私有协议（兜底）

如果 §6.1 证明芯片不说 NCI，那么可用的信息只有：

- 私有块结构（`pkt[0]` 类型 + `pkt[1]` 命令类，类 `0x10…0x90`）；
- 两套 4×32 字节 HMAC-SHA256 空密钥摘要（挑战/应答白名单）；
- 16 字节块、总量 50 字节的分块规律；
- 三个 IOCTL 码。

**但要复刻它必须同时拿到 Windows 侧的用户态对端**（`NFC.exe` 之外的华为 NFC 服务，例如华为电脑管家的 NFC 模块或 UWP 包），否则不知道 50 字节块里哪几位是「碰一碰」的载荷。而这个包里没有。所以路线 C 在现有材料下**不可完成**，只能作为后续拿到更多样本时的方向。

## 7. 待确认项（按优先级）

1. **从地址与 GpioInt 的精确参数** —— 跑一次 `ntag_nfc.ko` 或 `sudo i2cdetect -y -r 0` 即可（本报告未执行，因为当前会话没有 root）。
2. **芯片对 `CORE_RESET` 的应答** —— 决定 A/B/C 路线。
3. **`_CRS` 里 GpioIo 的数量与序号** —— 决定路线 A 的 GPIO 映射要不要改。
4. 芯片型号（若路线 A 走通，`nfctool` 的 `CORE_RESET_NTF` 会自报）。
5. 若走出 `0x60 00` NTF 且不是 NXP 的自定义 ID，再考虑 `nfcmrvl`（Marvell）/`st-nci`/`microread` 等其它 mainline 驱动。
