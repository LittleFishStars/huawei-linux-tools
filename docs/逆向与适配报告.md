# 华为 MateBook X Pro 2023 内置 NFC（ACPI\NTAG0001）Windows 驱动逆向与 Linux 适配报告

> 目标：把随机附带的 Windows 版 NFC 驱动逆向清楚，并在当前 Arch Linux 上落地可用的方案。
> 样本：`HUAWEI_MateBook_X_Pro_2023_13代酷睿版_NFC_23.2.3.0.zip`
> 分析机：MRGF-XX（MateBook X Pro 2023，13 代酷睿），内核 `7.2.10-arch1-1`

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 硬件是什么 | **NXP NTAG I2C plus 家族（NT3H2x11）双接口 NFC 标签**，ACPI 设备 `NTAG0001`（`\_SB_.PC00.NFC_`），挂在 Intel LPSS I2C 控制器 `0000:00:15.0`（i2c-0）的 **0x57**，另有一根 GpioInt（pin 176 → irq 213）作场检测（FD） |
| 怎么确定的 | 手机端标签工具读出：`NFC Forum Type 2`、`NFC-A NDEF`、只读、UID `1D D3 B4 D8 82 00 00`，两条 NDEF 记录（华为分享网址 + `application/vnd.huawei.handoff.ndefmsg`）。「Type 2 Tag + I2C 主机接口」是 NTAG I2C plus 的定义性特征 |
| Linux 内核认不认 | **认识设备，不认识驱动**：内核已按 ACPI `_CRS` 建好 i2c client `i2c-NTAG0001:00`，但 `nxp-nci_i2c` 的 ACPI 表只有 `NXP1001/1002/7471`，`pn544_i2c` 只有 `NXP5440`，没有能匹配 `NTAG0001` 的 |
| Windows 驱动是什么 | `SpbNfcDriver.sys`，**KMDF + CNG(HMAC-SHA256)** 私有驱动；不导入 `nfccx.sys`，无一行 NCI 编解码 |
| 它到底干什么 | **私有搬运工**：按 ACPI 资源打开 I2C 目标（`\Device\RESOURCE_HUB\<64bit id>`），把用户态的私有 16 字节块发给芯片、收回来、用空密钥 HMAC-SHA256 校验，再回给用户态 |
| 为什么驱动里没有 NFC 协议 | **因为不需要**。芯片自己就是一张完整的 Type 2 标签：NDEF 烧在片上，手机一贴由芯片自主应答，Windows 侧一个字节都不用发。驱动做的只是上层「碰一碰 → 华为分享」的联动逻辑 |
| Linux 上实际状态 | **已经能用**。手机贴上去能读到网址、能唤起华为分享 —— RF 侧完全由芯片自主完成，与主机装什么系统无关 |
| Linux 侧还能做什么 | 通过 I2C 直接读写这块标签（见 §6）；用 FD 中断做「手机靠近」事件源（`touchd.py`） |

**一句话**：这不是一块「需要驱动的 NFC 控制器」，而是一张**焊在主板上的、永远在线的只读 NFC 标签**。
Windows 驱动不是它的驱动，而是「碰一碰」功能的 PC 侧配套。Linux 下 NFC 本身天然可用，
剩下的价值是「主机能读写这块标签」与「中断事件」。

## 2. 硬件与固件侧事实（无需 root 即可复现）

```
$ ls /sys/bus/i2c/devices/ | grep NTAG
i2c-NTAG0001:00

$ cat /sys/bus/i2c/devices/i2c-NTAG0001:00/{name,modalias,uevent}
NTAG0001:00
acpi:NTAG0001:
MODALIAS=acpi:NTAG0001:

$ readlink -f /sys/bus/i2c/devices/i2c-NTAG0001:00
/sys/devices/pci0000:00/0000:00:15.0/i2c_designware.0/i2c-0/i2c-NTAG0001:00

$ readlink -f /sys/bus/i2c/devices/i2c-NTAG0001:00/firmware_node
/sys/devices/LNXSYSTM:00/LNXSYBUS:00/PNP0A08:00/NTAG0001:00     # ACPI 路径 = \_SB_.PC00.NFC_
```

要点：

1. **设备已被内核枚举**：`0000:00:15.0` 是 Intel Alder Lake-P PCH Serial IO I2C Controller #0（PCI ID `8086:51e8`），`i2c_designware` 驱动接管后建出 `i2c-0`，ACPI 又在其上建出 `NTAG0001:00` 这个 client。
2. `i2c-NTAG0001:00/` 下**只有 `name/modalias/uevent/power/` 和一个 `waiting_for_supplier`**——没有 `driver` 符号链接，说明它处于「等驱动」状态。
3. **从地址与 GPIO 中断号不暴露在 sysfs**，它们写在 ACPI `_CRS` 里。本项目已通过探测模块把它们拿到：

   ```
   ntag_nfc i2c-NTAG0001:00: 绑定成功: adapter=Synopsys DesignWare I2C adapter(nr=0) i2c_addr=0x57 irq=213
   ntag_nfc i2c-NTAG0001:00: 中断 213 已注册(上升沿, oneshot)
   ```

   对应 ACPI 原文（见 `analysis/acpi/nfc_device.asl`）：
   ```asl
   I2cSerialBusV2 (0x0057, ControllerInitiated, 0x00061A80,     // 400 kHz
       AddressingMode7Bit, "\\_SB.PC00.I2C0", 0x00, ResourceConsumer, , Exclusive)
   GpioInt (Edge, ActiveHigh, Exclusive, PullUp, 0x0000, "\\_SB.GPI0", 0x00, ResourceConsumer)
       { 0x0000 }                                              // → GNUM(0x09080010) = 176
   ```
   中断号 `176` 是 **GPIO 控制器的全局 pin 编号**，不是 IRQ；内核把它映射成 **irq 213**
   （`cat /proc/interrupts | grep 213` → `intel-gpio 176 ntag_nfc`）。极性为 **ActiveHigh + Edge**，
   与早先按下降沿注册的猜测相反 —— 实测只有上升沿能收到事件。
4. 同一条 i2c-0 上还挂着 `GXTP7863:00`（Goodix 触屏，GpioInt），说明这条总线上确实跑着「非 HID-over-I2C 的普通 ACPI client」。
5. 内核**已经带了 NFC 子系统**：`CONFIG_NFC=m`、`CONFIG_NFC_NCI=m`、`CONFIG_NFC_NXP_NCI=m`、`CONFIG_NFC_NXP_NCI_I2C=m`。
   但 `nxp-nci_i2c` 的 ACPI 别名只有 `NXP7471` / `NXP1002` / `NXP1001`，`pn544_i2c` 只有 `NXP5440`。
   **它们都是「NFC 控制器」驱动，而本机这颗芯片是「标签」，本就不该由它们驱动** ——
   这也是为什么手机能读、而 Linux 侧看起来什么都没发生。

## 2.5 芯片真实身份（手机端实测确定）

在把 Windows 驱动彻底拆完之前，先用 Android 的「标签工具」读一下这张标签，得到决定性证据：

| 字段 | 手机读出 | 意义 |
|---|---|---|
| 标签UID | `1D D3 B4 D8 82 00 00` | 7 字节 UID，NXP NTAG 系列前缀 |
| 标签技术 | `NFC-A NDEF` | ISO 14443-A + NDEF 封装 |
| **Forum类型** | **`NFC_FORUM_TYPE_2`** | **Type 2 Tag**（读写器可以直接用 READ/WRITE 命令操作）|
| 是否可写 | `false` | 用户内存被锁 |
| 设置只读 | `true` | 出厂烧成只读 |
| 记录1 | `https://consumer.huawei.com/en/support/huaweisharewelcome/` | URI 记录，TNF=Well-known, type=`U` |
| 记录2 | `application/vnd.huawei.handoff.ndefmsg` | **华为自定义 MIME 类型**，内容为二进制 |

$$\boxed{\text{「NFC Forum Type 2 Tag」 + 「I2C 主机接口」 = NXP NTAG I2C plus 家族（NT3H2x11）}}$$

ACPI HID 直接叫 `NTAG0001`，这本来就是 NXP NTAG 系列的命名习惯。型号进一步收敛的依据：

| 特征 | NTAG I2C plus（NT3H2111/2211） | 本机观察 |
|---|---|---|
| I2C 从地址 | `0x55` 或 `0x57`（由引脚选择） | **0x57** ✅ |
| RF 标准 | ISO/IEC 14443-A, NFC Forum Type 2 | **Type 2** ✅ |
| 主机接口 | 块寻址（bit7=I2C_LOCKED, bit6:0=块号） | 裸读行为吻合（见下） |
| 场检测引脚 | FD（field detect，RF 场出现时拉变） | irq 213 在手机靠近时计数 ✅ |
| 能量收集 | 可选（EH 引脚） | ACPI 无 GpioIo，未用 |

### 2.5.1 这一结论解释了之前所有异常现象

| 之前观察到的现象 | 现在得到解释 |
|---|---|
| 裸读能拿到「真正的 NDEF」（`55 04 consumer r.huawei.com/en/...`） | 裸读从芯片**内部指针**处开始读；上电后指针就停在 NDEF 区，所以看起来「能读到」 |
| 读完 53 字节后一直 `-110 ETIMEDOUT` | 读到内存末尾后不再给数据，**但拉低 SCL 不放总线** → 控制器超时。不是芯片坏，是没给地址 |
| 发 NCI `CORE_RESET` 全部 `-110` | 这颗芯片**根本不说 NCI**，它只会回 READ/WRITE/GET_VERSION/PWD_AUTH |
| `0x60`、`0x33` 等不存在地址也是 `-110` 而非 `-121` | 适配器被前一次超时搞死，之后所有传输都超时（假的），读数不可信 |
| 驱动里有 16 字节块、总长 50 字节、4×16=64 字节 SRAM、6 字节比对 | **完全对应 NTAG I2C plus 的内存/会话寄存器布局**：16 字节扇区、`F8h` 起的 SRAM、6 字节长度/字段 |
| 驱动里有**空密钥 HMAC-SHA256** 而不是明文 | 华为在上层做完整性标识，避免其他程序伪造「碰一碰」报文 |

### 2.5.2 正确的寻址方式

NTAG I2C plus 的 I2C 侧是**块寻址**的，不是简单 EEPROM：

```
写:  S + 0x57(W) + [block_addr] + data...            + P
读:  S + 0x57(W) + [block_addr] + Sr + 0x57(R) + 16B + NAK + P

block_addr: bit7 = I2C_LOCKED，bit6:0 = 块号
```

Type 2 内存布局：

| 块 | 内容 |
|---|---|
| `0x00` | UID0..2 + BCC0（**应为 `1d d3 b4 xx`**，用手机报的 UID 验证）|
| `0x01` | UID3..6 |
| `0x02` | BCC1 + internal + lock bytes |
| `0x03` | 能力容器 CC（应为 `E1 10 xx 00`）|
| `0x04` 起 | 用户内存，NDEF TLV（`03 <len> <ndef> FE`）|
| `F8h` 起 | 64 字节 SRAM（I2C 可直接访问，可传递快速数据）|

验证工具是 `tools/ntag_seek.py`：先读 block 0，UID 对上就把整块镜像拉下来解 NDEF。

```
HUAWEI_MateBook_X_Pro_2023_13代酷睿版_NFC_23.2.3.0.zip   (172,762 B, 外层含 .asc GPG 签名)
└── 同名内层 zip (170,823 B)
    └── NFC_23.2.3.0.exe     (196,280 B)  ← NSIS-3 Unicode 自解压
        └── NFC_23.2.3.0.exe (140,992 B)  ← 又是 NSIS
            └── $PLUGINSDIR/ …  真正载荷：
                ├── SpbNfcDriver.sys   (49,928 B)  PE32+ x86-64，2023-02-13 编译
                ├── SpbNfcDriver.inf   (4,480 B, UTF-16LE)
                ├── spbnfcdriver.cat   (签名目录)
                ├── devcon.exe         (88,592 B)  ← 微软 Device Console 工具
                └── install.cmd        (358 B)
```

`install.cmd` 的核心：`devcon.exe update SpbNfcDriver.inf "ACPI\NTAG0001"` —— 也就是说**华为是拿微软的 SPB 外设示例驱动改名、改成自己的私有协议**（INF 里 `DiskId1 = "SPB Test Tool Peripheral Installation Disk #1"` 明确暴露了血统）。

### INF 关键内容

```ini
Class      = HIDClass                     ; ← 挂在 HID 类下（不是 NFC 类！）
ClassGuid  = {745a17a0-74d3-11d0-b6fe-00a0c90f57da}
Provider   = "Huawei Device Co., Ltd."
DriverVer  = 02/10/2023,23.2.3.0
[Standard.NTamd64]
%SpbNfcDriver.DeviceDesc%=SpbNfcDriver_Device, ACPI\NTAG0001    ; ← 只匹配这一个 HID
[SpbNfcDriver_AddReg]
HKR,Settings,"isInterrupt",0x00010001,1    ; ← 注册表开关：要不要接中断
[SpbNfcDriver_Install.NT.Services]
AddService SpbNfcDriver, SPSVCINST_ASSOCSERVICE, StartType=3(DEMAND)
```

配合驱动里的 `WdfDeviceCreateDeviceInterface(&GUID_DEVCLASS_PORTS, …)`，用户在 Windows 上看到的是 `\Device\NFCDevice` 与 `\DosDevices\SPBNFCDRIVER` 两个名字，而**对外暴露的设备接口是 PORTS 类 GUID**——典型「不按规范办事的私有外设」。

`NFC.exe`（第一层解出来的那个）经检查是**纯 NSIS 安装器**（导入表只有 kernel32/user32/shell32/advapi32/ole32，节名 `.ndata`），**这个包里没有任何 NFC 用户态程序**。所以「NFC 应用逻辑」（碰一碰、配对、读写卡）不在我们手里。

## 4. `SpbNfcDriver.sys` 静态分析

工具：Ghidra 12.1 + objdump 交叉核对；产物 `/home/ylxc/nfc-re/sys.dis`（5591 行全反汇编）、Ghidra 工程。

### 4.1 总体形态

| 项 | 值 |
|---|---|
| 框架 | **KMDF**（`.kmdfclassbind$*` 段、`WdfVersionBind/WdfVersionBindClass` 来自 `WDFLDR.SYS`），DriverPoolTag `'SPBT'` |
| 导入（ntoskrnl） | `KeSetEvent/KeClearEvent/KeInitializeEvent`、`IoSetDeviceInterfaceState`、`IoRegisterDeviceInterface`、`IoWMIRegistrationControl`、`memcpy_s`、`RtlCopyUnicodeString/InitUnicodeString`、`MmGetSystemRoutineAddress`、`_vsnwprintf` |
| 导入（cng.sys） | `BCryptOpenAlgorithmProvider/GetProperty/CloseAlgorithmProvider/CreateHash/DestroyHash/HashData/FinishHash` |
| **没有导入** | `nfccx.sys`（NFC 类扩展）、`ntnfc.sys`、任何 NCI 相关符号 |
| 调用约定 | 函数表指针 `[0x140007378]`、驱动全局 `[0x140007380]`；每次 WDF 调用 = `rax = WdfFunctions[偏移]; rcx = WdfDriverGlobals; call __guard_dispatch_icall`，故反编译里看到的「第一个参数」其实是隐式的 WDF 全局 |

驱动一共 75 个函数、约 18.5 KB 代码，其中 4 个是 WPP/ETW 跟踪桩（`FUN_140009000` 一族），与业务无关。

### 4.2 设备上下文布局（从多个例程交叉验证得出）

| 偏移 | 类型 | 含义 |
|---|---|---|
| `+0x00` | WDFDEVICE | 设备对象 |
| `+0x08` | WDFQUEUE | 内部队列句柄 |
| `+0x10` | u32 | **I2C 连接的 64 位 ConnectionId 低半**（来自 ACPI `_CRS`） |
| `+0x14` | u32 | ConnectionId 高半 |
| `+0x18` | WDFINTERRUPT | 中断对象（`WdfInterruptCreate` 产生） |
| `+0x20` | KEVENT | 同步事件 |
| `+0x38` | u8 | `Settings\isInterrupt`（要不要用中断） |
| `+0x40` | WDFIOTARGET | 打开后的 I2C 目标句柄 |
| `+0x48` | WDF 对象 | 内部 I/O 请求/内存对象 |
| `+0x50` | 句柄 | 辅助对象 |
| `+0x58` | WDFREQUEST | 正在处理的客户端请求 |
| `+0x60` | WDFREQUEST | **可取消的挂起请求**（中断到来时完成它） |
| `+0x68/+0x69` | u8×2 | 两个状态/标志字节 |
| `+0x6c` | u32 | HMAC 模式（1 / 2，见 §4.5） |
| `+0x70` | BCRYPT_HASH_HANDLE | CNG 哈希句柄 |
| `+0x78` | BCRYPT_ALG_HANDLE | CNG 算法句柄 |
| `+0x90` | u32 | `HashDigestLength`（=32） |
| `+0x9a` … | 4×32B | **摘要表 A**（bank A） |
| `+0x11a` … | 4×32B | **摘要表 B**（bank B） |

设备上下文的 8×SHA256 摘要初值来自 `.rdata 0x140006190` 起的 0x100 字节常量，在 `EvtDeviceAdd` 里被 `memcpy_s` 拷进去——也就是说**驱动内置了两组（各 4 个）32 字节的期望值**，运行时用 HMAC-SHA256 算出来跟它们比。载体就是标准 SHA-256 的初始向量/轮常量，所以 `ghidra_detect_crypto_constants` 一撞一个准。

### 4.3 关键例程（函数级）

| 函数 | 角色 | 要点 |
|---|---|---|
| `FUN_140001b04` | `DriverEntry` | `WdfDriverCreate`，`EvtDriverDeviceAdd=FUN_140001000`，pool tag `'SPBT'`；随后 `WdfDriverCreateDeviceInterface`, `IoWMIRegistrationControl` |
| `FUN_140001000` | `EvtDeviceAdd` | 读注册表 `Settings\isInterrupt` → `+0x38`；建 2 个队列：队列0（`EvtIoRead=FUN_1400021c0`），队列1（`EvtIoWrite=FUN_140002b40`、`EvtIoDeviceControl=FUN_140002d20`、`EvtIoInternalDeviceControl=FUN_1400025c0`）；`WdfDeviceCreateSymbolicLink("\DosDevices\SPBNFCDRIVER")`；`WdfDeviceCreateDeviceInterface(GUID_DEVCLASS_PORTS)` |
| `FUN_140002770` | `EvtDevicePrepareHardware` | **资源解析**（见下） |
| `FUN_140002460` | 中断回调 | 取设备上下文，调 `FUN_1400039e4`；若有挂起请求则 `KeClearEvent(+0x20)` |
| `FUN_1400039e4` | 中断下半部 | 若 `+0x60` 有请求：`WdfRequestUnmarkCancelable` → 成功则 `WdfRequestComplete(req, 0)`，`STATUS_CANCELLED` 则静默返回 |
| `FUN_140003e50` | 取消例程 | 清 `+0x60`，`WdfRequestComplete(req, 0xC0000120=STATUS_CANCELLED)` |
| `FUN_140003fb0` | **打开 I2C 目标** | `id64 = *(u64*)(devctx+0x10)`；用 `"%0*I64x"` 格式化 → 与 `"\Device\RESOURCE_HUB\"` 用 `"%s%s"` 拼成设备名 → 填 0x88 字节的 `WDF_IO_TARGET_OPEN_PARAMS`（访问 `0xC0000000`、`ShareAccess=1`）→ `WdfIoTargetOpen`，句柄存 `+0x40` |
| `FUN_1400041e0` | 提交路径 | 请求存 `+0x58`，格式化后 `FUN_1400043a4` 真正发 I2C，失败走 `FUN_140003838` |
| `FUN_1400043a4` | Send | 建请求上下文，`WdfRequestSetCompletionRoutine(FUN_140003c90)`，然后 `WdfIoTargetSendIoctlSynchronously`/`WdfRequestSend` 一族，最后完成客户端请求 |
| `FUN_140003c90` | I/O 完成例程 | 从 `WDF_REQUEST_COMPLETION_PARAMS` 取 `IoStatus.Status/Information`，回填并调 `FUN_140003838` |
| `FUN_140003838` | 回客户端 | 若 `+0x58` 有请求则 `WdfRequestCompleteWithInformation` |
| `FUN_140001d80` | 加密初始化 | `BCryptOpenAlgorithmProvider("SHA256", 0x20)`（`0x20 = BCRYPT_ALG_HANDLE_HMAC_FLAG` → **HMAC-SHA256**）+ `BCryptGetProperty("HashDigestLength")` → `+0x90` |
| `FUN_140003570` | **私有协议状态机** | 见 §4.4 |
| `FUN_140004784` | 第二 I/O 处理 | 取请求内存块 → `FUN_140003570` 解析 → 写 `devctx+0x40` 目标 → 建内部请求 → `FUN_1400043a4` |

### 4.4 资源解析（`EvtDevicePrepareHardware`，已逐条对照汇编确认）

循环遍历 **Translated** 资源列表，用 `WdfCmResourceListGetDescriptor` 取描述符，看第一个字节（`CM_PARTIAL_RESOURCE_DESCRIPTOR.Type`）：

```
Type == 0x02 (CmResourceTypeInterrupt)
    → 记录中断描述符索引（重复出现则打 WPP 0xe）
Type == 0x84 且 [desc+4] == 2 (Class = SERIAL) 且 [desc+5] == 1 (Type = I2C)
    → 记录连接：
        *(u32*)(devctx + 0x10) = *(u32*)(desc + 8)
        *(u32*)(devctx + 0x14) = *(u32*)(desc + 0xc)     // 64 位 ConnectionId
      重复出现则打 WPP 0xc
```

- 找不到「连接」资源 → 直接失败返回 `0xC0000225`（`STATUS_NOT_FOUND`）；
- `+0x38`（注册表 `isInterrupt`）为 1 且找到中断 → 现场构造 0x68 字节的 `WDF_INTERRUPT_CONFIG`（`Size=0x68`、回调 `FUN_140002460`、`InterruptRaw/Translated` 来自两次描述符查询、`+0x58=1`、`+0x5c=2`）→ `WdfInterruptCreate` → 成功后 `KeInitializeEvent(+0x20, 1, 0)`；
- 最后调 `FUN_140001d80` 初始化 HMAC-SHA256。

> 结论：**驱动完全不含 I2C 地址**，它只持有 ACPI 给的「连接 ID」，再由 Resource Hub 把名字翻译成 I2C 传输参数。地址属于固件（ACPI `_CRS`）。

### 4.5 华为私有 16 字节协议（`FUN_140003570`）

用户态（Windows 上的 NFC 服务）通过 IOCTL / 写请求送进来的数据，被按如下规则解析：

```
len < 2                     → 失败
pkt[0] = 块类型, pkt[1] = 命令类
  0x10  (2..9 字节)  → FUN_1400032b4：读 pkt[6]
                           0x33 → 用 bank A 的两个 9 字节摘要做校验：命中 state=1，否则 state=2
                           0x02 → state=3                （进入"已认证"状态）
  0x20  (state!=3)   → FUN_140004914(pkt+2, bankB[0], bankB[1], 9,  ctx)
  0x30  (state!=3)   → FUN_140004914(pkt+2, bankB[2], bankB[3], 0x19, ctx)
  0x40  (state==3?)  → FUN_140004a74(pkt+0xb, 7, ctx)  或  FUN_140004914(pkt+2, bankB[4..], 0x29, ctx)
  0x50               → 仅 state==3 继续
  0x60               → state==3 时 FUN_140004a74(pkt+2, 9, ctx)
  0x70               → FUN_14000343c(pkt, 0x12, ctx)
  0x80               → FUN_140004a74(pkt+2, 0x10, ctx)
  0x90               → FUN_140004a74(pkt+2, 0xa,  ctx)
```

配套机制：

- **分块 HMAC 调度** `FUN_140004914`：按 `+0x6c` 的模式（1 用 bank A、2 用 bank B）把数据按 16 字节块（上限 0x32 字节）喂给 `FUN_140003190`/`FUN_14000306c`；模式非法或超长直接打 WPP 0x3e/0x3f 返回失败。
- **两套摘要表**（各 4×32 字节）—— 典型的**挑战/应答配对白名单**：驱动预置「哪台设备能配对」的期望值，用户态送来的 16 字节块与之比对，对了就把状态推到 `state=1/3`，之后才允许 0x50/0x60 这类数据通道命令。
- **IOCTL 面**：整份二进制里只出现三个自研 IOCTL 码 `0x4001C00` / `0x4001C04` / `0x4001C20`（`FUN_1400045c8`、`FUN_140003fb0`、`FUN_140003768`），**没有任何 `IOCTL_SPB_*`** —— 它不走 SPB 的 `IOCTL_SPB_EXECUTE_SEQUENCE`，用的是自己拼请求再 `WdfIoTargetSend…`。
- **全库没有任何 NCI 命令常量**（没有 `0x20 0x00 CORE_RESET`、`0x21 0x03 RF_DISCOVER`、`0x2F …`）—— **芯片协议不由驱动解释**，它只搬字节。

### 4.6 由 4.5 推出的架构判断（高置信）

```
Windows:  [NFC 服务/应用]  --私有 16B 块协议-->  SpbNfcDriver.sys  --原始 I2C 字节-->  芯片
Linux:                     --NCI/nfctool-->     nxp-nci(或本探针模块)  --I2C-->        芯片
```

也就是说：**华为把「NFC 协议栈 + 配对逻辑」放在了 Windows 用户态**（这解释了为什么包内只有驱动、为什么驱动里只有校验和搬运、为什么它连 nfccx 都不用）。这对我们是好消息——我们要替换的不是驱动，而是「协议栈」；而 Linux 恰好自带 NFC 协议栈（`net/nfc` + `nfctool`）。

## 5. 为什么不能把这个 Windows 驱动「移植」到 Linux

1. **框架不可移植**：整个驱动是 KMDF 回调模型（`EvtDevicePrepareHardware`/`WDFQUEUE`/`WDFINTERRUPT`/`WDFIOTARGET`），Linux 没有对应物，逐行翻译没有意义。
2. **传输通道是 Windows 专有**：`\Device\RESOURCE_HUB\<id>` 是 Windows SPB/Resource Hub 的私有设备名，Linux 的等价物是 ACPI 里已解析好的 `i2c_client`（内核已经帮我们建好了）。
3. **它不实现 NFC 协议**：把驱动搬过去也不会有任何可用功能——NFC 的 RF 发现、卡模拟、NDEF 读写全在别处。
4. **私有协议缺对端**：`0x10..0x90` 那套命令需要一个对应的用户态对端，而这个包**不含任何 NFC 应用**（`NFC.exe` 是 NSIS 安装器）。
5. 它只在 `isInterrupt` 打开时才用中断，且中断语义是「唤醒挂起的 16 字节应答」，与 NFC 标准的中断语义（数据就绪）不同。

**因此适配策略是「重新接入标准栈」，而不是「移植」。**

## 6. Linux 适配方案

### 6.0 路线重排

| 路线 | 适用前提 | 工作量 | 状态 |
|---|---|---|---|
| ~~A. 复用 mainline `nxp-nci`~~ | 芯片是 NXP NCI 控制器 | — | **已作废**：芯片是 Type 2 标签，不说 NCI |
| ~~B. 探针模块判类型~~ | 未知芯片 | — | **已完成**：正是靠它拿到 0x57 / irq 213，并测出 NCI 全超时 |
| **C. 把芯片当 I2C 标签读写** | 已确定 | 小 | **推荐**：标准 Type 2 内存模型 + NDEF，无需驱动 |
| **D. FD 中断作事件源** | 已确定 | 很小 | 已交付 `touchd.py`，可用作「手机靠近」触发器 |

$$
\boxed{\text{这颗芯片不需要「适配驱动」，它需要的是「被当作一块 I2C EEPROM + RF 标签」}}
$$

### 6.1 路线 C：当作 I2C 标签直接读写（主要方案）

因为芯片是 NFC Forum Type 2，它的内存模型是公开、标准的：16 字节一块，block 0 起是 UID/CC，
block 4 起是 NDEF TLV。所以在 Linux 上**不需要任何内核驱动**，走 `i2c-dev` 就够了。

```bash
cd ~/Projects/lib/huawei-ntag0001-nfc/tools
sudo python3 ntag_seek.py
```

脚本四步，每步都有明确判据：

1. **总线健康检查**（先行）：读 `0x60`，必须返回 `121 EREMOTEIO`。若返回 `110`，
   说明控制器已被上次超时搞死，**之后的读数全部不可信**，脚本直接停下并提示先恢复。
2. **扫描 `0x50`–`0x5F`**：NTAG I2C plus 有两个可选地址（`0x55` / `0x57`，引脚选择）。
3. **验证块寻址**：读 block 0，预期得到 `1d d3 b4 …`。同时试单字节/双字节地址方案，
   哪个对上 UID 哪个就是对的（预计是单字节）。
4. **拉全镜像并解析**：逐块读 `0x00`–`0x3F`，自动解析 CC（`E1 10 xx 00`）、TLV、
   NDEF 记录，并对 URI/TEXT/MIME 三种记录分别解码。

**全程只发 READ 与地址字节，绝不写入**——手机端报「设置只读 true」，用户区已被锁。

成功的话会得到类似：

```
block 0x00: 1d d3 b4 xx xx xx xx xx ...      ← UID，与手机对得上
block 0x03: e1 10 12 00                      ← CC: magic/version/size/access
block 0x04: 03 xx ... fe                     ← NDEF TLV
  记录1: TNF=1 type=b'U' → https://consumer.huawei.com/en/support/huaweisharewelcome/
  记录2: TNF=2 type=b'application/vnd.huawei.handoff.ndefmsg' → <二进制>
```

#### 6.1.1 为什么这条路以前没想到——三个认识误区

| 误区 | 实情 |
|---|---|
| 「NFC 设备就是 NCI 控制器」 | NFC 家族里有两类东西：**控制器**（说 NCI）与**标签**（说 Type 1/2/3/4 命令）。这颗是后者，且是带 I2C 主机口的 |
| 「它一直吐 NDEF，所以它是自己会发数据的智能芯片」 | NDEF 固定在片上内存里，裸读只是从内部指针处顺序吐内存；**主机不参与也不影响 RF 侧** |
| 「`-110` 表示芯片坏了」 | `-110` 是适配器超时；对这种块寻址芯片，**不给地址就拉 SCL** 是正常行为 |

### 6.2 路线 D：FD 中断作为事件源

芯片的 FD（field detect）引脚在 ACPI 里是一根 GpioInt（ActiveHigh，edge），
手机进 RF 场时拉变，内核已把它注册成 **irq 213**。`driver/ntag_nfc.c` 注册该中断；
`tools/touchd.py` 轮询 `/proc/interrupts` 里的计数，可在触碰时执行任意回调：

```bash
sudo insmod driver/ntag_nfc.ko probe_on_load=0    # 注意：不要让它主动写芯片
sudo python3 tools/touchd.py --exec 'notify-send "NFC" "手机碰触于 %s"'
```

实测确认：装载时计数为 0，手机贴近后跳到 4，**且全部落在 CPU0**，与 `IRQF_TRIGGER_RISING` 一致。
上一条「下降沿」的初始猜测已实测推翻。

### 6.3 已知未完成项

- `touchd.py --exec` 的回调链路**尚未实际跑过**（中断计数通路已验证，回调未验）。
- 块寻址读镜像**尚未执行**（需 root），待 `ntag_seek.py` 跑一次确认 block 0 = `1d d3 b4`。
- `handoff.ndefmsg` 的二进制内容尚未取出——那是「碰一碰」传给手机的真实载荷。

### 6.4 关于「碰一碰 / 华为分享」联动

Windows 侧的做法（由 `SpbNfcDriver.sys` 反推）：

```
手机贴上去 → 芯片自主把 NDEF（含 handoff.ndefmsg）交给手机
           → 手机侧识别到华为分享 → 通过 WiFi/BT 连回 PC
同时，PC 侧：FD 中断 → 驱动 → 用户态服务 → 读芯片确认是「分享」意图 → 接管后续
```

Linux 侧要复现**后半段**，缺的是华为 PC 侧服务（不在安装包里）。
但用 `touchd.py` + 自己的脚本可以做个**替代品**：FD 中断触发 → 扫二维码/发通知/开文件共享。
这部分取决于用户想要什么行为，不属于逆向范畴。

### 8.4 已实测确认 / 已推翻的判断（演进记录）

逆向过程中有一半工作是纠正早期猜测，这里如实记录，避免后来者重走：

| 判断 | 当时依据 | 结论 |
|---|---|---|
| 芯片是 NXP NCI 控制器（`nxp-nci` 可驱动） | ACPI HID 叫 `NTAG0001`，Android 内核有「Add driver support for NTAG」提交 | **已推翻**。NCI 控制器一律在 0x28，实测 0x57 且 NCI 命令全部超时 |
| 中断是下降沿 | 按「场检测通常低有效」的惯例猜 | **已推翻**。ACPI 明确写 `ActiveHigh`，只有上升沿能收到，计数器全落 CPU0 |
| 读回全零说明芯片无数据 | 当时不知道适配器已 wedged | **已推翻**。对照组 `0x60` 返回 `110` 而非 `121` 就说明总线已死，读数无效 |
| 芯片是自己吐数据流的私有芯片 | 裸读能连续读出 NDEF | **已推翻**。那是内部指针顺序读，NDEF 本就存在片上 |
| Windows 驱动是「NFC 驱动」 | 文件名叫 SpbNfcDriver | **部分修正**。它是「碰一碰」的 PC 侧配套，不是标签的驱动——标签不需要驱动 |
| 触摸板失灵必须重启 | `recover_bus.sh` 弄坏了 i2c-hid | **已解决**。`fix_touchpad.sh` 重绑 client 即可，不用重启 |

**教训**：I2C 调试必须**先跑对照组**。没有对照组的读数，在适配器 wedged 后全是噪声——
这次的「全零」「全超时」「地址不存在」三个结论，根因都是同一个已被打死的控制器。
